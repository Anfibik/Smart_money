## 1. Коротко о продукте

`Smart Money` — локальное iOS-приложение для управления личным бюджетом. Это не только журнал расходов: приложение автоматически распределяет доход и стартовый капитал между тремя верхнеуровневыми категориями, а затем между карточками внутри них с учётом процентов, денежных минимумов, максимумов и приоритетов.

Категории в текущем интерфейсе:

- `Основные` (`essentials`) — обязательные расходы;
- `Желаемые` (`wants`) — необязательные расходы;
- `Финансы` (`savings`) — подушка, долг, кредит, инвестиции, цели и другие финансовые карточки.

Нераспределённые деньги хранятся в отдельном пуле `Свободный капитал`. Он участвует в стартовом формировании бюджета, покрытии расходов и ручных переводах.

Приложение работает полностью локально, без аккаунта, backend и сетевых интеграций.

## 3. Технологии и общая архитектура

Стек:

- Swift + SwiftUI;
- Combine (`ObservableObject`, `@Published`);
- Foundation;
- Charts для аналитики;
- XCTest;
- UIKit только в реализации фиксированной темы (`UIColor`).

Архитектура — прагматичный MVVM:

```text
Smart_moneyApp
    -> ContentView
        -> BudgetViewModel (главное состояние и оркестрация)
            -> BudgetAllocationEngine (правила распределения)
            -> PersistenceService (снимок бюджета)
            -> BudgetHistoryStorage (история операций)
        -> StartOnboardingBuilder (первичная конфигурация и preview)
        -> HistoryAndStatisticsViewModel
            -> BudgetStatisticsService
```

Главное архитектурное правило: UI не должен напрямую менять деньги. Все доходы, расходы, переводы, изменения карточек, откат операций и применение onboarding-конфигурации проходят через `BudgetViewModel`. Алгоритм распределения не следует дублировать во View или другом сервисе — его источник истины `BudgetAllocationEngine`.

## 4. Основной пользовательский поток

### Первый запуск

`ContentView` проверяет `@AppStorage("has_completed_start_onboarding_v2")`. Если настройка не завершена, открывается недоступный для интерактивного закрытия `StartOnboardingFlowView`.

Онбординг состоит из 5 шагов:

1. `Финансы и жилье` — средний месячный доход, текущий капитал/долг, тип и стоимость жилья, имеющаяся иностранная валюта.
2. `Иждивенцы` — взрослые, пожилые родственники, дети до 12 лет, животные, автомобиль и кредит.
3. `Выбор стратегии` — соотношение трёх главных категорий.
4. `Карты потребностей` — просмотр активных карт и выбор рекомендованных карт.
5. `Ваш финансовый план готов` — итог, дефициты, свободный капитал, выбор покрытия потребностей и/или Подушки.

После подтверждения `BudgetViewModel.applyStartOnboardingConfiguration` полностью применяет рассчитанную конфигурацию, а `has_completed_start_onboarding_v2` становится `true`.

### Основной экран

`ContentView` содержит:

- верхнюю строку добавления дохода;
- `CategoryAccordionView` со сворачиваемыми категориями и карточками;
- блок Свободного капитала;
- боковое меню с отдельными маршрутами `История` и `Статистика`;
- полный сброс с повторным запуском онбординга.

Обычный tap по карточке открывает расход. Long press открывает управление карточкой/средствами. Пользовательские карточки можно добавлять и удалять; системные удалить нельзя.

Приложение принудительно использует тёмную тему через `.preferredColorScheme(.dark)`. Основные строки интерфейса сейчас на русском языке.

## 5. Доменная модель

### Категории и карточки

`ExpenseCategory` содержит процент от общего дохода и массив `Subcategory`.

У `Subcategory` есть:

- стабильный `UUID`;
- имя и SF Symbol;
- `isSystem` и стабильный `SystemSubcategoryKey`;
- базовый процент внутри категории;
- денежные `minLimit` и `maxLimit`;
- приоритет `low / medium / high`;
- режим финансирования `automatic / manualOnly`;
- валюта баланса ручной карточки;
- накопленный `spentAmount`.

`systemKey`, а не отображаемое имя, должен использоваться для бизнес-идентификации системных карточек. Decoder умеет восстанавливать ключ по старому русскому имени для совместимости со старыми сохранениями.

### Стратегии

- `Стабильность`: Основные 60%, Желаемые 15%, Финансы 25%.
- `Баланс`: Основные 55%, Желаемые 20%, Финансы 25%.
- `Рост Капитала`: Основные 50%, Желаемые 15%, Финансы 35%.

### Канонические приоритеты

`BudgetViewModel.normalizePriorityRules()` принудительно нормализует приоритеты:

- все пользовательские карточки — `low`;
- Основные: при аренде `Жилье` — `high`, при собственном жилье `Питание` — `high`, остальные системные — `medium`;
- Желаемые: `Шопинг` — `high`, остальные системные — `medium`;
- Финансы: при наличии `Долга` он — `high`, иначе `Подушка` — `high`; остальные системные — `medium`.

Переданный из UI `priority` для новой пользовательской карточки фактически не сохраняется: карточка создаётся с `low`. Это осознанный текущий инвариант.

## 6. Каталог системных карточек

Единый каталог находится в `App/Models/SystemCardCatalog.swift`. Он задаёт категорию, описание, стандартный процент, минимум, приоритет, доступность и funding mode.

### Всегда активные

- Основные: `Жилье`, `Питание`, `Здоровье`, `Гигиена`, `Транспорт`.
- Желаемые: `Шопинг`, `Досуг`.
- Финансы: `Подушка`.

### Условные

- `Дети` — если `childrenCount > 0`;
- `Животные` — если `petsCount > 0`;
- `Долг` — если стартовый капитал отрицателен;
- `Кредит` — если пользователь указал кредит.

### Рекомендуемые, включаемые пользователем

- Желаемые: `Хобби`, `Путешествия`, `Рестораны`, `Подарки`, `Спорт`, `Красота`, `Подписки`.
- Финансы: `Инвестиции`, `Бизнес`, `Валюта`, `Цель`.

`Цель` включается только при положительной целевой сумме; эта сумма становится максимумом карточки. `Валюта` автоматически включается, если на старте указана положительная валютная сумма.

## 7. Формулы стартовой настройки

Расчёты выполняет `StartOnboardingBuilder`. Для первоначального формирования все денежные значения округляются до целой гривны с сохранением суммы распределения.

Проценты активных основных карточек:

- Жилье: аренда 25%, своё жильё 10%;
- Питание: `20% + 4% * взрослые иждивенцы + 2% * дети`;
- Здоровье: `3% + 0,5% * взрослые иждивенцы + 1% * дети + 5% * пожилые иждивенцы`;
- Гигиена: 5%;
- Дети: 10% при наличии детей;
- Животные: 3% при наличии животных;
- Транспорт: 10% с авто, 5% без авто.

Денежные минимумы:

- Жилье — введённая месячная стоимость;
- Питание — `8 000 * (1 + 0,8 * взрослые иждивенцы) + 5 000 * дети`;
- Здоровье — максимум из процента бюджета категории Основные и `500 * общее количество людей`;
- Гигиена — 500 ₴;
- Дети — 10% бюджета категории Основные;
- Животные — 1 000 ₴ на животное;
- Транспорт — 2 000 ₴ с авто, 1 000 ₴ без авто;
- Кредит — введённый месячный платёж;
- Долг — модуль отрицательного стартового капитала, одновременно min и max;
- Подушка — шесть месячных сумм обязательного проживания, одновременно min и max.

`monthlyMinimumExcludingEmergency` исключает из суммы Подушку и Долг. `mandatoryLivingMonthly` включает жильё, питание, здоровье, гигиену, детей, животных, транспорт и кредит.

### Важная семантика стартового капитала

Стартовое распределение ограничено реальными положительными деньгами:

```text
initialDistributionAmount = min(monthlyIncome, positiveCapital)
remainingFreeCapital = positiveCapital - initialDistributionAmount
```

То есть указанный доход служит месячным планом, но приложение не создаёт виртуальные деньги сверх фактического капитала. Первоначальное распределение не создаёт событие дохода в истории — это проверяется тестами.

На итоговом шаге пользователь независимо выбирает:

- покрыть карточные дефициты из Свободного капитала;
- пополнить Подушку из Свободного капитала.

Порядок onboarding-покрытия: Основные → Долг → Подушка (если включена) → остальные дефициты. Внутри группы учитываются приоритеты, а недостаточная сумма делится пропорционально дефицитам.

## 8. Алгоритм распределения дохода

`BudgetAllocationEngine.applyIncomeDelta` работает так:

1. Делит новый доход между главными категориями по процентам стратегии.
2. Внутри категории сначала закрывает дефициты денежных минимумов.
3. Дефициты идут по приоритетам `high → medium → low`; внутри одного уровня неполная сумма делится пропорционально потребности.
4. Для Основных есть защита от ситуации, когда одна high-карта поглотит всё и оставит обязательные lower-priority карты без денег: при таком сценарии сумма делится по всем дефицитам Основных.
5. Остаток распределяется между автоматическими карточками по их процентным весам с учётом `maxLimit`.
6. То, что невозможно распределить, уходит в Свободный капитал.

Ручные карточки (`manualOnly`) полностью исключены из автоматического гривневого распределения, донорства и суммы категории.

## 9. Расходы и переводы

Для автоматической карточки доступны две стратегии оплаты:

- `Карточки сначала` (`categoryFirst`);
- `Капитал сначала` (`freeCapitalFirst`).

`expenseFundingPreview` заранее показывает источники денег. При category-first порядок фактически такой:

1. остаток выбранной карточки;
2. свободные суммы других automatic-карточек той же категории выше их защищённых минимумов, доноры идут `low → medium → high`;
3. Свободный капитал;
4. если всё ещё не хватает — подтверждаемое принудительное покрытие из сумм ниже минимумов других карточек, автоматически или вручную.

Если денег недостаточно, операция атомарно откатывает промежуточные изменения.

Другие операции:

- перевод из automatic-карточки в Свободный капитал;
- перевод из Свободного капитала в automatic-карточку с соблюдением max;
- автоматический/ручной внутренний перевод между карточками категории;
- добавление и редактирование карточки с проверкой 100% внутри категории;
- удаление только пользовательской карточки с возвратом остатка в Свободный капитал;
- перенос превышения нового max в Свободный капитал.

## 10. Ручная валютная карточка

Системная карточка `Валюта` имеет `fundingMode = manualOnly`, процент и min/max принудительно обнуляются. Поддерживаются `USD, EUR, GBP, CHF, PLN, CAD, JPY, CNY, RUB`.

Доступно:

- прямое ручное пополнение в валюте карточки без изменения Свободного капитала;
- покупка валюты за Свободный капитал с вводом валютной суммы, гривневой суммы и курса;
- обратная конвертация валюты в Свободный капитал по введённому курсу;
- расход только в пределах собственного валютного остатка;
- смена кода валюты без автоматической конвертации существующего баланса;
- откат переводов через историю, когда у события сохранён `undoDelta`.

Валютная карточка не может финансировать расход другой карточки. Её расходы и движения сейчас помечены `affectsStatistics = false` и не входят в основную финансовую статистику.

## 11. История, статистика и undo

Типы событий:

- `income`;
- `expense`;
- `transferToFreeCapital`;
- `transferFromFreeCapital`;
- `categoryReallocation`;
- `manualCardDeposit`;
- `currencyConversion`.

Доходы и обычные расходы входят в статистику. Переводы и валютные/manual операции по умолчанию не входят.

История хранит snapshot-имена/иконки, поэтому старые записи не зависят от последующего переименования карточки. Финансовые операции сохраняют `BudgetOperationDelta`; `revertHistoryEvent` применяет обратную дельту и удаляет запись. Связанные внутренние переводы имеют `parentEventID`, скрываются как отдельные строки и откатываются вместе с родительским расходом. Есть fallback-группировка legacy-записей по времени и именам.

Статистика поддерживает:

- месяц;
- год;
- всё время после последнего полного сброса;
- фильтры истории;
- общий доход, расход, net result, количество операций;
- крупнейший и средний расход;
- разбивку расходов по категориям и всем карточкам внутри категорий.

## 12. Хранение данных

### Текущее состояние бюджета

`PersistenceService` кодирует `BudgetPersistedState` в JSON и хранит `Data` в `UserDefaults` по ключу `budget_state_v2`. Предыдущая корректная версия хранится отдельно в `budget_state_v2_backup`.

Сохраняются настройки, суммы по UUID карточек, Свободный капитал, месячные входящие/исходящие трекеры и baseline категорий. Запись debounced на 0,35 секунды; при уходе scene из `.active` вызывается принудительный flush.

### История

`BudgetHistoryStorage` хранит JSON-файл `budget_history_v1.json` в `Application Support/<bundle-id>/`, а предыдущую корректную версию — в `budget_history_v1.json.backup`. Запись остаётся debounced и atomic, с flush при смене scene phase.

### Прочие ключи UserDefaults

- `has_completed_start_onboarding_v2` — завершение онбординга;
- `app_install.*` — дата, версия и build первого запуска.

Если основной budget snapshot или история не декодируются, приложение автоматически восстанавливает данные из backup и показывает уведомление. Если повреждены обе копии, запись блокируется, чтобы пустое состояние не перезаписало данные; пользователь получает явный экран для сброса бюджета либо только истории.
